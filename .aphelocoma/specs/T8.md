# T8 — Migrate real-world v0.2 Hamilton state

## Goal

Make the explicit v0.2 project-state migration accept realistic legacy task and ledger shapes while
preserving history, rollback safety, and strict validation for every event written after migration.

## Scope

- Normalize omitted nullable `task` / `to` event fields.
- Rename legacy task `depends_on` to `dependencies` without data loss.
- Preserve optional legacy task notes and Hamilton update metadata.
- Record an explicit v0.2 history baseline so pre-v0.3 lifecycle drift remains auditable without
  weakening post-migration protocol checks.
- Bind that exact legacy prefix and its task-status snapshot to separate SHA-256 digests in a
  canonical migration marker.
- Keep check/apply backup, staging validation, rollback, privacy, and Git containment guarantees.
- Reinstall and redeploy the reviewed local fix to Claude and Codex.

## Non-scope

- Applying migration to the advisor's `field_operations` project.
- Editing or committing any file in that external project.
- Rewriting or fabricating legacy task history.
- Changing schema/protocol version numbers, adding a host, pushing, tagging, publishing, or releasing.

## Interfaces / files touched

- `src/aphelocoma/hamilton_state.py`
- `skills/aph-hamilton/references/state.schema.json`
- `skills/aph-hamilton/references/PROTOCOL.md`
- `docs/migration-v0.3.md`
- `docs/documentation-assertions-v0.3.md`
- `tests/test_hamilton_state.py`

## Acceptance criteria

- [ ] A failing test first reproduces omitted nullable ledger keys, `depends_on`, legacy notes/metadata,
  and lifecycle history that predates strict replay.
- [ ] `check` remains byte-for-byte read-only.
- [ ] `apply` keeps a byte-for-byte original backup and produces schema-valid current state.
- [ ] Successful migration preserves every legacy ledger event in order, adding only missing nullable
  keys, and records the exact legacy prefix plus task-status snapshot as a history baseline.
- [ ] Separate SHA-256 digests and one canonical marker bind the exact legacy prefix and task-status
  snapshot; a self-declared, advanced, or snapshot-tampered baseline is rejected.
- [ ] Strict lifecycle validation begins immediately after the baseline and rejects invalid new events.
- [ ] Native v0.3 projects without a baseline retain full-history strict validation.
- [ ] Conflicting `depends_on` / `dependencies` input fails closed and rolls back.
- [ ] The focused regression, full suite, live validator, Bash/actionlint/diff/Python 3.9 gates, and an
  isolated-copy rehearsal of the advisor's legacy state pass before independent review.
