# T15 — Prepare the v0.3.0 release

## Goal

Everything the v0.3.0 release needs that does not require pushing, merging, or tagging — those stay
the advisor's. When this task is done, the advisor should be able to run the release from a written
checklist without deciding anything mid-flight, and no document should claim more than has actually
been verified.

## Context the writer must not get wrong

**CI has never run on this code.** The last push to `origin/develop` was 2026-07-04; all 23 commits of
v0.3 are local. The CI matrix is ubuntu-latest and macos-latest against Python 3.9 and 3.x. Everything
so far has been verified only on macOS with Python 3.14.4. **Linux and the advertised Python 3.9 floor
are unverified anywhere.** No document may state or imply otherwise.

**The old install command will break after the merge.** The published command
`curl -fsSL https://raw.githubusercontent.com/PhyoYazar/aphelocoma/v0.2.0/install.sh | bash` pins only
the installer script to the tag. That script runs `git clone "$REPO_URL" "$TOOL_DIR"` with no ref, so
it clones whatever `main` points at, into `~/.aphelocoma/tool` — the directory v0.3's transactional
installer manages — and then runs `aph setup`, which v0.3 answers with
`Error: Unknown command 'setup'`. Both halves were confirmed by running them, not inferred. The v0.2.0
tag is immutable, so no code change reaches those users; documentation is the only mitigation.

**The advisor has decided `install.sh` stays as it is** — it keeps cloning the default branch, so
"install" means "latest released". Do not change installer behavior.

## Scope

1. **`CHANGELOG.md`.** `## [0.3.0] — Unreleased` becomes a released heading. Match the existing
   `## [0.2.0]` style, which carries no date — do not invent a release date, since the advisor controls
   when the tag is cut.
2. **`docs/release-readiness-v0.3.md`.** It says `Status: READY`, assessed 2026-07-24 at T6, and
   predates T7–T14 — the deployed-runtime fix, the v0.2 state migration, and the entire progress-board
   feature. It never mentions the board or `STATUS.md`. Refresh it to cover the repository as it stands
   now, and change the status to one that is true before CI has run: what is verified locally, on what
   platform, and what remains pending. Name the two unverified things explicitly.
3. **`docs/migration-v0.3.md`.** Add the old-install-command breakage: who hits it, the exact failure,
   and what to run instead. Someone upgrading from v0.2 is exactly the reader who has that command
   saved.
4. **`docs/release-v0.3.0.md` (new).** Two parts: draft GitHub release notes for v0.3.0, written for a
   user rather than a changelog reader; and the advisor's step-by-step release checklist — push, watch
   CI, what to do if it is red, merge to `main`, tag, publish — with the readiness-doc second pass
   called out as its own step, since that document cannot honestly read READY until CI is green.

## Non-scope

- `install.sh` and any installer behavior. The advisor decided it stays.
- Pushing, merging, tagging, or publishing anything.
- `VERSION` — already `0.3.0`.
- A README CI badge, and the README's illustrative progress-board snippet, which shows stale sample
  task titles but is plainly an example of the output format rather than a claim about this project.
- Any code or test change.
