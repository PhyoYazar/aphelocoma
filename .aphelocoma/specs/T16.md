# T16 — Record the green CI run in the readiness report

## Goal

CI has now run, and it passed. `docs/release-readiness-v0.3.md` was written before that and says so.
Update it to state what is now true, and update the test that pins its wording in the same commit —
because changing one without the other breaks CI on the next push.

## The evidence

The first hosted CI run for this project:

- Run: CI #1, <https://github.com/PhyoYazar/aphelocoma/actions/runs/30197582782>
- Commit: `e8d87de15ef793d4ebe02f0d86b4bf0b34cdde2c`, branch `develop`
- Result: success, all four matrix jobs, about one minute
- Jobs: `ubuntu-latest / Python 3.9`, `ubuntu-latest / Python 3.x`,
  `macos-latest / Python 3.9`, `macos-latest / Python 3.x`

This is the first time Linux and the advertised Python 3.9 floor have been verified anywhere. Before
this run, everything had only ever been checked on macOS with Python 3.14.4.

The run also produced four **warnings** — `actions/checkout@v4` and `actions/setup-python@v5` target
Node.js 20, which GitHub deprecated and is now forcing onto Node.js 24. Nothing failed. Record it
honestly as a known warning with no effect on the result; do not fix the action versions here.

## Scope

1. **`docs/release-readiness-v0.3.md`.**
   - Line 3's status, `READY FOR CI — NOT YET READY TO RELEASE`, is now out of date. Give it a status
     that is true after a green run.
   - Line 184's `Hosted runner execution: pending first CI run` becomes the actual result: the run
     reference, the commit, and what passed.
   - Anywhere the document names Linux or Python 3.9 as unverified or pending, correct it. Search the
     whole file rather than only the two known lines.
   - Record the Node.js deprecation warnings.
2. **`tests/test_release_smoke.py`.** `test_release_metadata_and_report_are_final` asserts three literal
   substrings, one of which is `Hosted runner execution: pending first CI run`. Update that assertion to
   match the new wording.

## The constraint that matters most

That test exists to stop this document drifting into claims nobody checked. **It must come out of this
task at least as strong as it went in.** Do not delete the assertion, and do not weaken it to something
that would pass against any text. Whatever replaces it must fail if the CI evidence is removed or
emptied — assert on the specific new content, the way the current assertion does.

If a stronger assertion is available cheaply, take it.
