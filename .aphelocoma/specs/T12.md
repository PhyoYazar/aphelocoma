# T12 — Close the holes the T11 review found in the staleness check

## Goal

The staleness warning is what stops a missed board from going unnoticed. The T11 review found four
ways it fails quietly, plus one ordering bug that would leave the committed board permanently one
task behind. Close them.

## Scope

Five defects, all found by the independent T11 review:

1. **A stamp ahead of the ledger is trusted forever.** `_validate_status_report()` only warns when
   `behind > 0`, so a stamped seq greater than the ledger's — reachable via a truncated or rolled-back
   ledger — silently disables the check for good. Worse, the writer and the validator use two
   different definitions of "last seq": `_last_ledger_seq()` takes the last non-blank line, the
   validator takes `max()` over all events.
2. **A false remediation message.** When the ledger is unreadable at write time the stamp reads
   `... from ledger seq unknown` — a stamp that is present and readable — but the validator reports
   that the file "carries no readable generated stamp".
3. **A vacuous test.** `test_written_status_file_is_committable_not_ignored` passes against `HEAD`,
   where `--write` does not exist and no file is created, because `git check-ignore` works on the
   pathname rather than the file.
4. **A failed `--write` suppresses the board.** The write happens before any printing and inside the
   same `try`, so a permission problem costs the advisor the board entirely instead of degrading to a
   printed-but-unwritten one.
5. **The board is written after the commit.** `PROTOCOL.md` §5.6 says the board is printed after each
   `task_completed` commit. Taken literally, every commit's `STATUS.md` is one task stale and the
   working tree always carries an uncommitted board.

## Non-scope

- The narrowed board content, `--json`, the four trigger points, and the warn-not-error decision.
  All are settled and reviewed.
- Schema, protocol version, or migration changes.
- The T11 review's remaining note about the deployed `validate.py` shim preferring the installed
  runtime. That is pre-existing T7 behavior, correct by design, and resolved by reinstalling.
- Version bump, tag, push, or release.

## Acceptance criteria

- [ ] Failing tests are written first for every fix below.
- [ ] A stamped seq **ahead** of the ledger's last seq produces its own warning telling the reader the
  board is inconsistent with the ledger and to regenerate it. It is never silently trusted.
- [ ] The writer and the validator read the ledger's last seq through **one shared function**, so the
  two can no longer disagree. A test pins that they agree on a non-contiguous ledger.
- [ ] The `seq unknown` case reports that the stamp names no sequence — not that the stamp is missing.
  The two states have distinct, accurate messages.
- [ ] `test_written_status_file_is_committable_not_ignored` asserts the file exists before checking
  `git check-ignore`, and a test proves it fails against a tree where `--write` produced nothing.
- [ ] A failed `--write` still prints the board: the board goes to stdout first, the write failure is
  reported on stderr, and the exit code still signals the failure. Under `--json`, stdout stays exactly
  one parseable document.
- [ ] `PROTOCOL.md` §5.6 states that the board is regenerated **before** the task's commit so that
  `STATUS.md` lands in the same commit as the state it describes, and that a committed board is
  therefore never stale by construction. The four trigger moments themselves do not change.
- [ ] The staleness check still never errors and never blocks `resume` — every new path is a warning
  with exit 0.
- [ ] The full standard-library suite, `aph doctor`, and the Hamilton validator all pass. The validator
  must be run against the **repository bundle**, not the installed runtime, so the new checks actually
  execute — state how you forced that in the handoff.
